# WUI D3D12 integration

`wui::d3d12::Renderer` (`include/wui/backends/d3d12.hpp`, target `wui_d3d12`)
records draw packets into command lists the host owns. It never creates a
queue, executes a list, signals or waits on a fence, creates a swap chain,
or starts a thread. Everything below is covered by `wui-d3d12-lifetime`
(device-free bookkeeping) and `wui-d3d12` (native) in the
`win-d3d12-debug` and `win-d3d12-release` presets.

```bat
call out\vulkan-env.cmd
cmake --preset win-d3d12-debug
cmake --build --preset win-d3d12-debug
ctest --preset win-d3d12-debug
```

`wui_d3d12` links `d3d12`, `dxgi` and `d3dcompiler`. The shaders
(`backends/renderer/d3d12_shaders.hlsl`) are embedded at configure time and
compiled with `D3DCompile` as `vs_5_0`/`ps_5_0` inside `create`. No D3DX or
DXC is used.

## Host / renderer split

| Host owns | Renderer owns |
| --- | --- |
| Device, direct queue, command allocators and lists | Root signature (one SRV table, one static linear-clamp sampler, two 4-value root-constant blocks) |
| Fences, completion values, `Signal`, waits | Pipeline state for `rtv_format` / `sample_count` |
| Render target, its RTV, its resource state | One shader-visible CBV/SRV/UAV heap, partitioned per frame slot |
| Submission order and presentation | Per-slot upload-heap buffer (vertices, indices, texture staging) |
| Rebinding its own state after `record` | Default-heap textures keyed by snapshot (handle, revision, extent, alpha, identity) |

## Creating

```cpp
wui::d3d12::Config config;
config.device = device;                       // feature level 11_0 or higher
config.rtv_format = DXGI_FORMAT_R8G8B8A8_UNORM; // or B8G8R8A8_UNORM
config.max_frames = 3;                        // frame slots the host will use (1..64)
config.max_textures = 256;                    // SRVs per slot
auto created = wui::d3d12::Renderer::create(config);
```

`create` fails with a specific status:

- `invalid_argument`: null device, zero frames, textures or samples, or more than 64 frames.
- `unsupported`: a target format other than RGBA8/BGRA8 UNORM (tested with `R16G16B16A16_FLOAT`).
- `capacity`: `max_frames * max_textures` above the 1,000,000-descriptor shader-visible heap limit.

`create` also returns `unsupported` for a device below feature level 11_0, a
non-blendable target format, or an unsupported sample count. No available
test device triggers those paths.

The tests create the renderer on every hardware adapter that accepts a
feature-level 11_0 device and on WARP (`IDXGIFactory4::EnumWarpAdapter`).
They exercise only single-sample `R8G8B8A8_UNORM` targets.

## Per frame

```cpp
// 1. Host: reset the slot's allocator and list; pick a completion value
//    greater than the fence's current completed value.
wui::d3d12::FrameSlot slot{index, fence, ++fence_value};

// 2. Uploads: CopyTextureRegion from the slot's upload buffer plus
//    COPY_DEST -> PIXEL_SHADER_RESOURCE barriers, recorded into `list`.
auto prepared = renderer->prepare(slot, list, packet);

// 3. Host: transition the target to RENDER_TARGET (and clear if wanted).
// 4. Draw. The renderer sets its root signature, pipeline, descriptor heap,
//    render target, viewport and per-batch scissor, then draws in packet order.
renderer->record(ticket, list, {rtv, width, height});

// 5. Host: rebind its own root signature, pipeline and descriptor heaps
//    (SetDescriptorHeaps) before recording more of its own work, close the
//    list, ExecuteCommandLists, then Signal(fence, slot.completion_value).
renderer->submitted(std::move(ticket));

// 6. Any time later, without blocking:
renderer->collect();
```

- The list passed to `prepare` must execute before, or in the same submission as, the list passed to `record`. The tests use one list for both.
- `record` binds the renderer's own shader-visible heap. The host's heaps are no longer bound afterward, so it must call `SetDescriptorHeaps` again.
- The target size must equal the packet viewport times its scale (rounded), or `record` returns `invalid_argument` and leaves the ticket prepared.
- A packet with no batches or indices records nothing. Its slot still completes normally.
- Scissor rectangles come from the shared `physical_scissor` helper, as in every other renderer. The batch clip is scaled to physical pixels, edges within 1/1024 px of a pixel boundary are snapped, and the result is floored and ceiled outward, then clamped to the target. A test at scale 1.25 with clip edges 81.6/77.6 (101.9999981/96.9999981 physical) checks that no fringe column or row is added.
- A second `record` of the same ticket returns `invalid_frame`.

## Frame slots and completion

Each slot index is one ticket. `prepare` returns:

- `busy` while the slot's previous submission has not reached its completion value. It first polls that slot's fence, so a completed slot is reused without a separate `collect`.
- `invalid_frame` when `completion_value` is not above the fence's current completed value, or after `shutdown`.
- `capacity` when the packet has more textures than `max_textures`. Nothing is recorded and the slot is not consumed.

`collect` polls `GetCompletedValue` for every submitted slot and never waits.
When a slot completes it drops that frame's packet lease and fence reference.
The tests fill all three slots while the queue is blocked on a gate fence
(a real `ID3D12CommandQueue::Wait`, not a simulated value). A fourth
`prepare` then returns `busy`, and `collect` succeeds while keeping every
revision resident.

`shutdown` returns `busy` while any slot is prepared, recorded or submitted
but not complete. It succeeds once every fence has completed, is idempotent,
and later `prepare` calls return `invalid_frame`. Destroying the renderer
with frames still pending is a host contract violation; the destructor
asserts on it in Debug, which no test exercises.

### Abandoning a frame

If the host discards a list without executing it, it calls
`abandon(std::move(ticket))`. Destroying an unsubmitted `PreparedFrame` does
the same. The slot becomes free at once. Textures uploaded only by that
frame are released at once, because their copy never ran. The tests abandon
both a prepared-only and a recorded frame, then render the same packet
correctly.

## Textures and retirement

Native textures are default-heap `R8G8B8A8_UNORM` resources. Each is keyed
by the snapshot's handle (slot, generation), revision, width, height, alpha
mode and snapshot object identity. Handle and revision alone are not unique:
two texture stores can issue equal handles. The tests render an original
snapshot, then a different-pixel snapshot with the same handle and revision,
then the original again, and check that the second frame differs and the
first and third match. An entry whose snapshot has expired never matches
again. Every slot that
uses one adds a reference. A texture is released only when no slot
references it, and only if one of these is also true:

- another revision of the same handle was uploaded later;
- its CPU snapshot expired;
- its upload was abandoned unexecuted.

An upload recorded by a slot that has not been submitted yet is never
shared with another slot. That slot uploads its own copy instead.

In the tests, revisions 1, 2 and 3 of the fixture checker stay resident
while their slots are in flight. Revisions 1 and 2 retire only after every
referencing fence completes. Revision 1 then renders again from a fresh
upload, and revision 3 retires after that frame completes.

Each slot has its own upload buffer. A slot's buffer is reused only after
that slot's fence completed, and it grows when a frame needs more. The tests
upload a 1024×1024 texture through the 256 KiB initial buffer.

## Device removal

`GetCompletedValue() == UINT64_MAX` is treated as device removal. The
renderer enters a terminal state: `prepare`, `collect` and `shutdown` return
`device_lost`, and the host must create a new renderer on a new device.
Resource creation in `prepare` that fails with
`DXGI_ERROR_DEVICE_REMOVED`/`RESET`/`HUNG` is also mapped to `device_lost`;
that path is untested.

The tests cover only **simulated** removal: an injected completed-value
source returns `UINT64_MAX` while the real device stays healthy. Physical
device removal is never provoked. A replacement renderer on the same device
then renders the retained packet.

## Common conformance suite

`tests/conformance/d3d12_backend.cpp` (`wui_conformance_d3d12`, CTest
`wui-conformance-d3d12-warp`) runs the shared conformance suite as a host
would. It has its own direct queue, one allocator and list per frame slot,
one fence, a single-sample `R8G8B8A8_UNORM` target and a readback buffer
laid out with `GetCopyableFootprints` (256-byte row pitch). `--driver warp`
(the default) uses `EnumWarpAdapter`, and `--driver hardware` uses DXGI
adapter 0. The debug layer is always enabled; Debug builds also enable
GPU-based validation.

- In-flight: the adapter makes the queue wait on a gate fence that only `collect_all` signals. The renderer then accepts three frames and returns `busy` for the fourth.
- Recreate: `shutdown`, destroy the renderer, release every device object, create a new device and renderer. `D3D12CreateDevice` hands back the live device for an adapter, so a private-data marker proves the new device is distinct.

Results on WARP and on the RTX 2080 Ti: the suite passes with the debug layer
clean in every group. Compared with the D3D11 WARP reference, D3D12 WARP is
byte-identical in all 88 cases. Hardware is within tolerance in all 88 (max
channel diff 2).

## Validation evidence

Every native test enables `ID3D12Debug` before creating any device. Debug
builds also turn on GPU-based validation (`ID3D12Debug1`). After each case,
the queue is drained and the `ID3D12InfoQueue` must hold zero warnings,
errors and corruption messages. A run with the texture barrier removed on
purpose produced a GPU-based-validation error on every adapter, so the check
does catch barrier mistakes. The fixture cases use the same expected pixels
as the D3D11 reference test, plus the checker, clip and scale-2 pixels used
by the Vulkan test.

Not exercised by tests: MSAA targets, `B8G8R8A8_UNORM` targets, separate
upload and draw lists, multiple queues, upload-ring wrap inside the renderer
(the renderer restarts a free slot's ring at offset 0; wrap and overflow are
covered only by the device-free ring tests), and physical device removal.
